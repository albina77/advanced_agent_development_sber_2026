# Вымышленные сценарии памяти

`scenarios.json` — восемь сценариев, 17 сессий и 70 пользовательских реплик. Это сценарии с ожидаемым поведением; фактический результат живого прогона хранится отдельно в `run_log.md` и `run_log.json`.

Разбор первичных ошибок, каскадных последствий и ошибок, скрытых за PASS, — в [error_classification.md](error_classification.md); машинная разметка — в `error_classification.json`.

Формулировки созданы заново с учётом общих особенностей разговорного ввода: короткие команды, недостающие параметры, исправления, паузы. Суммы, идентификаторы клиентов, последовательности событий и фоновые объявления вымышлены. Исходные логи, строки таблицы и привязка примеров к реальным клиентам отсутствуют. Просьбы сохранить предпочтения добавлены специально для проверки памяти.

В текущем наборе фоновые реплики не помечены словами «объявление терминала», «сосед» или пояснениями об адресате. Неоднозначные фразы вроде «Да, закажи мне чай» не должны подтверждать операцию. Пять замен перечислены в `background_changes.json`; исходный набор и предыдущий прогон сохранены в `runs/before_natural_background`. Проверки действий и сохранности памяти остались прежними.

| ID | Что проверяем |
|---|---|
| M01 | Предложение прошлого номинала в новой сессии, новая сумма, два отдельных подтверждения |
| M02 | Приоритет явного предпочтения над последним разовым выбором |
| M03 | Замена старого предпочтения новым |
| M04 | Разделение памяти клиентов |
| M05 | Удаление и отсутствие восстановления данных |
| M06 | Разные сроки хранения профиля и эпизодов |
| M07 | Смысловой поиск и влияние свежести |
| M08 | 34 реплики в первой сессии: 30 адресованных и четыре фоновых; затем новая сессия |

## Как использовать

Автоматический прогон из корня репозитория:

```sh
./atm_agent/run.sh --synthetic-memory-scenarios
```

Команда использует живые GigaChat и Cloud.ru, подготавливает RAG при необходимости, создаёт отдельную временную базу для каждого сценария и сохраняет логи рядом с набором. Рабочая база клиента не используется. Между сессиями Store закрывается и открывается заново, а граф создаётся заново. M06 использует тестовые часы, M07 — два подготовленных эпизода. Для M07 и M08 worker запускается отдельным Python-процессом. Формулировки не меняются; провал ожидания записывается в лог, остальные реплики продолжают выполняться.

Повторный запуск заменяет `run_log.md` и `run_log.json`. Для отдельного сценария и другого каталога результата:

```sh
./atm_agent/run.sh --synthetic-memory-scenarios --case M01 --output /private/tmp/atm-M01
```

Код выхода 1 означает, что есть проваленные проверки; подробности остаются в логе. Последний прогон 31.10.2026 выполнил все 70 реплик: 58 прошли структурные проверки, полностью прошли M03, M04, M07 и M08. В M08 все 37 шагов прошли: сумма 12000 ₽ названа клиентом в реплике 2 и восстановлена агентом в реплике 33 без повторения суммы клиентом. Подтверждение в реплике 34 отправило withdraw 12000/500. Отдельная выдержка с проверками — `m08_resume_check.json`.

Для завершения M08 добавлены намерение `capabilities` для вопросов об операциях и действие `keep` для просьбы не менять предпочтение. В текущем прогоне вопрос о внесении не начал операцию, профиль сохранился. Потеря явно названного номинала в M01, M02, M05 и M06 остаётся. Прогон до этих изменений (53/70) сохранён в `runs/before_m08_resume_fix`; самый первый (45/70) — в `runs/before_natural_background`. Реплики в версиях различаются, поэтому сравнение общих чисел не является строгой оценкой улучшения качества.

Автоматические проверки оценивают команды, слоты, предложения из памяти, сроки, удаление, фон и источники. Полный текст ожидаемого поведения сохранён рядом с каждым ответом: его содержательность и удобство нужно оценивать при чтении лога, а не по одному статусу PASS.

Для каждого сценария нужна отдельная пустая временная база. `setup` описывает подготовку, `sessions` — обращения клиентов, `turns` — реплики и ожидаемое поведение. Ожидания проверяют состояние и действия, а не дословный ответ.

В интерактивном режиме:

```sh
./atm_agent/run.sh --client-id synthetic_client_a --memory-db /private/tmp/atm-public-demo.sqlite3 --trace
```

Передавайте `text` из выбранного сценария по одной реплике. Значение `client_id` имитирует идентификацию по карте и задаётся приложением, не текстом клиента. Для следующей сессии того же клиента используйте `/new`; для проверки сохранности после перезапуска завершите программу и запустите её с тем же файлом базы и идентификатором. Для другого клиента перезапустите с его `--client-id`.

Временный файл должен быть новым перед началом каждого независимого сценария. Между сессиями одного сценария его сохраняют. Учебный софт сообщает успешную выдачу; реальных банковских операций нет.

Для смыслового поиска M07 и реплики о памяти в M08 подготовьте записи отдельным worker:

```sh
./atm_agent/run.sh --memory-worker --memory-db /private/tmp/atm-public-demo.sqlite3
```

M06 требует программного управления часами, M07 — подготовки двух эпизодов с разными датами. Их нельзя воспроизвести только вставкой реплик в терминал. Примеры такой подготовки находятся в `scenarios/memory_lifecycle.py` и тестах памяти. В M08 нужны подготовленный RAG и доступ к API; перед вопросом о сохранённом выборе worker можно запустить из второго терминала.

Поле `expected` описывает требование, а не измеренный результат. Неуспешные шаги сохраняются в отчёте вместе с ответами и фактическим состоянием.
